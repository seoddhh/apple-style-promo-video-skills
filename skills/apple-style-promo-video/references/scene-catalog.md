# 장면 카탈로그 — 기능을 증명하는 UI 장면

타이포 장면이 혹하게 만들면, UI 장면이 믿게 만든다. 기능 구간은 아래 유형 중에서 고르고, 앞에 투톤 헤드라인이나 단어 교체 같은 타이포 무브를 붙인다 ([typography-playbook.md](typography-playbook.md)).

공통 규칙: **결과 화면에는 반드시 구체적인 데이터**(실제 이름, 숫자, 문장)가 있어야 한다. "분석 완료", "최적의 결과" 같은 추상적인 문구로 결과를 대신하지 않는다.

UI 화면 없이 타이포만으로 만드는 경우에는 1·2·3·5번을 글자로 바꿔 쓴다. 예: 입력 문장 → 결과 문장으로 바뀌는 글자 변신, "2시간 → 3분" 숫자 히어로, Before/After 투톤.

## 1. 플로우 데모 (가장 기본, 3~5초)
실제 UI에서 입력 → 처리 → 결과를 한 흐름으로.
- 구성: 화면(폰/브라우저 목업 또는 떠 있는 카드) 1개 안에서 상태가 바뀐다. 장면을 끊지 않는다.
- 기본은 목업 없이 핵심 UI 조각을 크게 띄우는 것이다 (design-system.md UI 요소). 지도·사진 위에 떠 있는 컨트롤이 있으면 Liquid Glass로 그린다.
- 순서: 입력 필드에 타이핑(글자 단위 등장, 커서 깜빡임) → 버튼 탭(리플+눌림) → 처리 표시(점 3개 또는 스켈레톤 0.4~0.6초) → 결과 카드가 stagger로 채워짐 → 핵심 값 하나에 포인트 컬러 하이라이트.
- 헤드라인은 화면 위/옆에 "무엇을 했는지"가 아니라 "무엇을 얻었는지"로 쓴다. (✗ "사진을 업로드하세요" ✓ "사진 한 장이면 견적 끝")
- 처리 시간은 짧게. 로딩을 오래 보여주면 느린 제품처럼 보인다. 빈 화면 대신 스켈레톤을 먼저 띄우고 그 자리가 실제 데이터로 바뀌게 한다.
- 완료 순간은 짧은 확인 피드백 하나로 (✓ Draw On, 버튼 Replace). 큰 축하 연출은 엔드카드 전 마지막 결과에만.

## 2. Before / After (2~3초)
기존 방식의 고통과 제품 사용 후를 한 화면에서 대비.
- 좌우 분할(16:9) 또는 상하 분할(9:16). 왼쪽은 `--sub` 회색·채도 낮게, 오른쪽은 포인트 컬러 한 곳.
- 색 차이만으로 구분하지 않는다. 양쪽 위에 "기존" / "서비스명" 라벨을 붙인다.
- 또는 와이프: 같은 자리에서 clip-path inset으로 Before를 밀어내며 After가 드러남.
- 양쪽의 **같은 지표**를 비교한다 (시간 2시간 → 3분, 단계 12개 → 1개).

## 3. 수치 증거 (1.5~2.5초)
- 숫자 히어로(typography-playbook ⑩): 큰 숫자 카운트업 + 작은 단위 + 회색 한 줄. 숫자는 화면을 압도하게 (16:9 기준 240~340px).
- 둘 이상이면 가로로 나열하고 0.15초 stagger, 한 번에 최대 3개.
- 비교 막대: 두 막대가 동시에 자라다가 우리 막대만 계속 자라며 포인트 컬러로 채워짐.
- 출처 없는 수치는 쓰지 않는다. 사용자가 준 수치만 쓰고, 예시라면 "예시" 표기.
- 숫자 아래 한 줄은 단위 설명이 아니라 **그래서 무엇이 좋은지**로 쓴다 (✗ "누적 사용자 12,000명" ✓ "12,000명이 매주 써요").
- 차트를 쓰면 위에 결론 한 문장을 둔다. 막대·선·링 같은 익숙한 형태만 쓴다 (motion-recipes.md 데이터).

## 4. 기능 그리드 → 포커스 (3~4초)
기능이 많을 때 한 장면으로 폭을 보여준다.
- 2×3 또는 3×2 카드 그리드가 stagger로 등장(아이콘 + 기능명 2~6자).
- 카메라가 한 카드로 줌인(그리드 전체를 scale+translate) → 그 카드가 풀스크린 UI로 연속 변환 → 해당 기능의 플로우 데모로 이어진다.
- 포커스되지 않은 카드는 opacity .35.

## 5. 데이터 흐름 / 작동 원리 (3~4초)
AI 제품, 개발자 도구, B2B에서 "어떻게 되는가"를 보여줄 때.
- 왼쪽 입력 소스(아이콘 2~4개: 문서, 메일, DB, API) → 가운데 엔진(로고 또는 원) → 오른쪽 출력(결과 카드).
- 연결선은 stroke-dashoffset으로 그려지고, 선을 따라 작은 점(데이터 패킷)이 이동한다.
- 엔진에 도착한 조각들이 합쳐져 결과 카드 하나가 된다 (연속 변환).
- 아키텍처 박스를 5개 넘게 그리지 않는다. 기술 설명이 아니라 "재료가 결과가 된다"를 보여주는 장면이다.

## 6. 비교 (2~3초)
- 체크리스트 표: 행(기준 3~4개) × 열(기존 방식 / 우리). 우리 열의 ✓가 위에서부터 spring으로 찍힌다.
- 경쟁사 이름은 사용자가 허락했을 때만. 기본은 "기존 방식", "수작업".
- ✓만 포인트 컬러로 두지 말고 ✓/✗ 모양 자체로 구분되게 한다.

## 7. 타임라인 / 사용자 여정 (3~5초)
- 가로 선이 그려지며 단계 노드(3~5개)가 순서대로 켜진다. 현재 단계에 포커스 링.
- 각 노드 아래에 그 단계의 미니 UI 카드가 팝업. 전체 여정을 보여준 뒤 한 단계로 줌인해 플로우 데모로 이어갈 수 있다.
- 로드맵, 온보딩 과정, 주문→배송 흐름에 쓴다.

## 8. 코드·터미널 (2~4초)
개발자 도구, API, CLI, 오픈소스.
- 다크 에디터 카드(radius 24, 모노 폰트) 안에서 코드가 줄 단위로 타이핑된다. 신택스 컬러는 3색 이내.
- 핵심 한 줄(예: `npm i xxx`, 함수 호출 1줄)만 하이라이트하고 나머지는 흐리게.
- 실행 결과가 옆 카드나 브라우저 프리뷰로 즉시 나타나야 한다. 코드만 보여주고 끝내지 않는다.
- 코드는 실제 동작하는 짧은 예시를 쓴다. 사용자의 README나 docs에서 가져온다.

## 9. 결과 갤러리 (2~3초)
생성형 제품(이미지, 문서, 디자인, 추천 결과)에서 결과의 다양성을 보여줄 때.
- 결과 카드 5~9개가 무한 스크롤처럼 흐르거나(translateX 등속이 아닌 eio로 구간 이동), 부채꼴로 펼쳐진다.
- 한 장을 집어 확대해 디테일을 보여주고 끝낸다.

## 10. 실제 후기·사용 사례 (2초)
- 사용자가 **실제로 받은** 후기·사례만. 지어낸 후기, 가상의 인물 이름은 쓰지 않는다.
- 인용 카드 1~2개, 이름은 사용자가 공개 허락한 형태로(이니셜, 직함).
- 후기가 없으면 이 장면 대신 수치 증거나 Before/After를 쓴다.

## 비트 하나를 구성하는 예 (4.5초)

| 시간 | 장면 | 내용 |
|---|---|---|
| 0–0.8 | 맥락 | 헤드라인 1줄 단어 등장 "회의 끝나면" |
| 0.8–3.0 | 플로우 데모 | 녹음 파일이 앱 카드에 드롭 → 처리 점 → 요약 3줄 + 할 일 체크리스트가 stagger |
| 3.0–3.8 | 결과 강조 | 할 일 하나가 포인트 컬러로 하이라이트, 담당자 칩이 slot에 착지 |
| 3.8–4.5 | 증거 | "요약 2시간 → 30초" 카운트다운 숫자 |

결과(3.0 이후)가 비트 길이의 1/3 이상 되도록 한다. 입력만 길고 결과가 순식간에 지나가면 내용이 약해 보인다.
