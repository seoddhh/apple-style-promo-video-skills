# 애플 스타일 모션그래픽 홍보영상

AI 영상 모델 없이 **HTML/CSS/JS로 장면을 코딩하고, 헤드리스 Chromium으로 프레임 단위 캡처해 ffmpeg로 MP4를 만든다.** 한글과 UI가 깨지지 않고, 타이밍을 프레임 단위로 조절하고, 고치면 바로 다시 렌더링할 수 있다.

만들 수 없는 것: 실사 인물·손·물리 제품 촬영 느낌, 음악. 실사가 꼭 필요하면 그 컷만 다른 도구로 만들어 편집에서 섞는 방식을 제안한다. 음원을 주면 비트에 맞춰 타이밍을 조정해 합친다.

## 이 스킬의 원칙: 내용이 주인공이다

좋은 홍보영상은 "멋진 인트로"가 아니라 **"이 제품이 무엇을 해주는지 구체적으로 봤다"** 는 느낌을 남긴다. 그래서:

- **오프닝은 짧게.** 브랜드 인트로·캐릭터 팝·파티클 연출로 시작하지 않는다. 첫 1~2초는 질문, 결과 화면, 핵심 수치 같은 **내용 훅**으로 연다. 로고 리빌은 엔드카드에서 한 번만.
- **시간의 60% 안팎을 핵심 기능 비트에 쓴다.** 비트마다 맥락 → 행동 → 결과 → 증거를 실제 UI와 구체 데이터로 보여준다.
- **장식 모션(파티클, 스쿼시, 캐릭터 인사)은 영상 전체에서 2회 이하.** 모션은 인과관계를 보여줄 때 쓴다 (입력이 결과가 되는 과정, 데이터가 모이는 과정).
- **한 화면 한 메시지.** 헤드라인 1문장 + 시각 요소 1그룹.

### 시간 배분 기본값

| 구간 | 비율 | 20초 기준 | 내용 |
|---|---|---|---|
| 훅 | ≤10% (최대 3초) | 0–2s | 질문 한 줄, 결과 화면 미리보기, 충격적 수치 중 하나 |
| 문제 | 10~15% | 2–5s | 타깃이 실제로 겪는 상황 1개, 구체적으로 |
| 핵심 비트 | 55~65% | 5–16s | 기능 2~3개 × 비트 (맥락→행동→결과→증거) |
| 증거·차별점 | ~10% | 16–18s | 수치, 비교, 실제 사용 규모 |
| 엔드카드 | 8~10% | 18–20s | 로고 + 슬로건 + CTA/URL |

기능이 4개 이상이면 2~3개만 비트로 풀고 나머지는 "기능 그리드" 한 장면으로 묶는다. 모두 비트로 풀면 각각이 얕아진다.

## 1단계: 자료 조사 → 제작 브리프 (코딩 전에 반드시)

질문보다 조사가 먼저다. 사용자가 준 URL, 레포, README, 피그마, 발표자료, 캡처를 먼저 읽고 채울 수 있는 칸은 채운다. 그 다음 **아래 브리프를 초안 상태로 보여주고** 빈칸과 추정한 칸을 확인받는다. 추정한 칸은 `(추정)`으로 표시한다.

### 제작 브리프 질문지

**A. 목적과 시청 맥락** — 영상의 형태를 정한다
1. 어디서 틀어지나? 발표장 대형 스크린 / 인스타·유튜브 쇼츠 / 랜딩페이지 히어로 / 앱스토어 프리뷰 / 링크드인·X 피드 / 전시 부스 루프
2. 소리가 켜진 채로 보나? (피드·쇼츠는 대부분 무음 → 화면 텍스트가 모든 정보를 담아야 함)
3. 비율과 길이: 16:9 / 9:16 / 1:1 / 4:5, 15·20·30·45·60초
4. 보고 난 뒤 시청자가 해야 할 행동 한 가지 (가입, 다운로드, 투자 미팅, 부스 방문, 기억만 하기)

**B. 메시지와 핵심 내용** — 영상의 60%를 채울 재료다. 가장 자세히 묻는다
5. 제품 한 줄 정의 (누가 / 무엇을 / 어떻게 더 낫게)
6. 타깃 사용자와 그들이 겪는 **구체적 장면** 하나 ("회의록 정리에 매주 2시간"처럼)
7. 보여줄 기능 **우선순위 1~3위**와 각 기능에서:
   - 사용자가 무엇을 입력·조작하나
   - 결과로 무엇이 나오나 (실제 예시 데이터가 있으면 최고)
   - 기존 방식보다 무엇이 나은가
8. 증거로 쓸 수 있는 것: 수치(사용자 수, 시간 절감, 정확도), 수상, 파트너, 실제 후기 (실제 것만. 지어내지 않는다)
9. 시청자가 딱 하나 기억할 문장 (슬로건 후보 또는 핵심 메시지)
10. 쓰면 안 되는 표현, 경쟁사 언급 여부, 아직 공개 안 된 기능

**C. 자산과 브랜드**
11. 로고(SVG/투명 PNG), 마스코트, 브랜드 컬러, 폰트
12. 실제 앱 화면 캡처 또는 배포 URL (없으면 UI를 조판하고 "시연용 화면"으로 표기)
13. 레퍼런스 영상이나 원하는 톤 (미니멀·차분 / 경쾌·빠름 / 테크·정밀 / 따뜻·감성)
14. 화면 언어 (한국어 / 영어 / 병기)

**D. 제작 조건**
15. 마감, 음원 유무, 발표 중 말과 겹치는지 (겹치면 텍스트를 줄이고 템포를 늦춘다)

### 묻는 방법

- 선택형(A1~A3, C13)은 AskUserQuestion으로 한 번에 묻는다 (최대 4문항).
- 서술형(B5~B10)은 조사로 채운 초안을 보여주고 "틀린 곳과 빈칸만 알려주세요"라고 묻는다. 초안을 최대한 채워서 가야 사용자 부담이 적다.
- **B7(기능과 결과 예시)이 비어 있으면 진행하지 않는다.** 여기가 부실하면 영상이 추상적인 타이포 나열이 된다. 사용자가 "알아서"라고 하면 조사한 내용으로 예시 데이터를 만들고 "시연용 임의 데이터"임을 영상과 답변 양쪽에 밝힌다.
- 나머지 칸은 비어 있어도 기본값으로 진행하고, 어떤 기본값을 썼는지 한 줄로 알린다.

## 2단계: 메시지 설계 → 샷 리스트

브리프가 확정되면 코딩 전에 두 가지를 보여주고 확인받는다.

**① 비트 시트** — 핵심 기능마다 한 줄

| 비트 | 맥락 (상황) | 행동 (UI 조작) | 결과 (화면에 나오는 것) | 증거 | 장면 유형 |
|---|---|---|---|---|---|
| 기능 1 | ... | ... | 구체 데이터 | 수치/비교 | 플로우 데모 |

**② 샷 리스트** — 시간 / 화면 / 모션 / 자막. 시간 배분이 위 비율을 따르는지 확인한다.

장면 유형은 [references/scene-catalog.md](references/scene-catalog.md)에서 고른다 (플로우 데모, Before/After, 수치 증거, 기능 그리드→포커스, 데이터 흐름, 비교, 타임라인, 코드·터미널). 영상 유형별 골격은 [references/story-templates.md](references/story-templates.md)를 본다.

## 3단계: 핵심 비트 프리뷰 → 전체 렌더

톤 확인용 첫 렌더는 **오프닝이 아니라 가장 중요한 핵심 비트 1개(5~8초)** 다. 제품 이해도와 UI 퀄리티가 여기서 드러나기 때문이다. 확인받은 뒤 전체로 확장한다.

## 환경 준비

```bash
which ffmpeg && python3 -c "import playwright" && echo ok
# 없으면: pip install playwright --break-system-packages && python3 -m playwright install chromium
mkdir -p promo && cd promo && npm i pretendard      # 한글. 영문 전용이면 npm i @fontsource/inter
cp <skill>/assets/template.html promo.html
cp <skill>/scripts/render.py <skill>/scripts/qa_frames.py .
```

첨부 에셋은 작업 폴더로 복사해서 쓴다. 원본은 수정하지 않는다.

## 핵심 아키텍처: 장면 모듈 + `render(t)` 순수 함수

`assets/template.html`이 이 구조로 되어 있다. 이 구조를 지키는 이유는 **어느 프레임이든 t만으로 화면이 결정되어야** 부분 렌더, 재렌더, 프레임 검수가 모두 가능하기 때문이다.

1. CSS transition, @keyframes, requestAnimationFrame, setTimeout 금지. 모든 상태는 t로부터 계산한다.
2. 장면은 `SCENES` 배열에 `{id, dur, draw(lt, t)}`로 등록한다. 전역 `render(t)`가 모든 장면을 돌며 **범위 밖 장면은 매 프레임 숨김을 명시**하고, 범위 안 장면만 `draw`를 호출한다. `draw` 안에서 early return 하지 않는다 (잔상의 원인).
3. 장면 시작 시간은 `dur`의 누적으로 자동 계산된다. 한 장면 길이를 바꾸면 뒤가 자동으로 밀린다. 장면끼리 겹쳐야 하는 전환은 `overlap`으로 지정한다.
4. 이동할 요소의 도착 좌표는 `measure()`에서 `getBoundingClientRect()`로 측정한다. 측정 전에 부모 transform을 `none`으로 초기화한다.
5. 비율은 URL 파라미터 `?format=16:9|9:16|1:1|4:5`로 바뀐다. 레이아웃은 `--W`, `--H`, `--safe` CSS 변수와 `body[data-format]` 선택자로 잡아 비율 변경에 버티게 한다.

렌더링:
```bash
python3 render.py promo.html --format 16:9 --out promo.mp4                 # 전체 (길이는 페이지의 DURATION)
python3 render.py promo.html --from 5 --to 12 --fps 15 --out preview.mp4   # 핵심 비트만 빠르게
```

## 품질 검수 (매 렌더마다)

```bash
python3 qa_frames.py promo.mp4 promo.html      # 장면 중간 + 전환 ±0.1s 프레임을 grid.png로
```
grid.png를 Read로 직접 본다.

**내용**
- [ ] 소리 없이 봐도 제품이 무엇을 해주는지 이해된다
- [ ] 핵심 비트마다 결과 화면에 구체 데이터(이름, 숫자, 실제 문장)가 보인다. "AI가 분석합니다" 같은 추상 문구만 있는 장면이 없다
- [ ] 훅이 전체의 10% 이하이고, 핵심 비트가 55% 이상이다
- [ ] 시연용 임의 데이터가 있으면 화면 구석에 작게 표기했다

**화면**
- [ ] 전환 순간 이전·다음 장면이 겹쳐 번쩍이지 않는다
- [ ] 하이라이트·버튼 채움 중간에 글자가 배경과 같은 색이 되지 않는다
- [ ] 이동한 요소가 slot에 정확히 착지한다
- [ ] 텍스트가 잘리거나 한 글자만 줄바꿈되지 않는다. 안전영역 밖에 텍스트가 없다
- [ ] 폰트가 fallback으로 렌더링되지 않았다
- [ ] 한 화면에 포인트 컬러가 두 곳 이상 경쟁하지 않는다

고친 뒤 다시 렌더링하고 **검수를 통과한 최종본만** 전달한다.

## 수정 요청 대응

- "더 풍부하게 / 내용이 약해": 장식 모션을 늘리지 말고 비트에 **결과 데이터나 증거**를 추가한다 (수치 카운트업, Before/After, 결과 예시 한 줄 더).
- "더 인터랙티브하게": 핵심 비트 안의 UI 조작(탭, 입력, 드래그, 스크롤)을 늘린다. 오프닝에 추가하지 않는다.
- "기능 X도 보여줘": "자리 비켜주기" 전환으로 2~3초 비트를 추가한다. `SCENES`에 넣으면 뒤가 자동으로 밀린다.
- "더 짧게": 훅·엔드카드를 먼저 줄이고, 그다음 비트 수를 줄인다. 비트 안의 결과 장면은 마지막까지 지킨다.
- 색·문구 변경: CSS 변수와 텍스트만 바꾸고 다시 렌더링한다.
- 실제 캡처를 받으면 조판 UI를 폰/브라우저 목업 + 캡처로 교체한다.
- 음원: `ffmpeg -i promo.mp4 -i music.mp3 -c:v copy -c:a aac -shortest -af "afade=t=out:st=<끝-1.5>:d=1.5" final.mp4`. 비트 시점에 맞춰 장면 `dur`를 조정한다.
- 여러 비율이 필요하면 16:9를 먼저 완성하고 `--format`만 바꿔 레이아웃을 확인·보정한다. 9:16은 텍스트를 1.3배 키우고 요소를 세로로 쌓는다.

## 전달

- 완성 MP4를 SendUserFile로 보내고, 요청이 있으면 `promo.html`, `render.py`도 함께 보낸다.
- 답변에는 비트 구성(어떤 기능을 어떤 장면으로 보여줬는지)과 바뀐 컷만 짧게 설명한다. 시연용 임의 데이터가 있으면 반드시 밝힌다.
